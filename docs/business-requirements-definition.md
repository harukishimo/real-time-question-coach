# Realtime Question Coach 業務要件定義書

作成日: 2026-07-08

## 0. 作成方針

本書は、既存資料を元に Realtime Question Coach の業務要件を定義する初版である。会議後の議事録作成ではなく、会話中の聞き漏れを減らす業務価値を中心に置く。

作成にあたり、次の観点を分離してレビューし、最終的に統合した。

| 観点 | 主な確認内容 |
| --- | --- |
| 定義書作成 | 章立て、用語、MVP境界、品質チェック観点 |
| 要件定義 | 業務目的、対象利用者、業務要件、受入基準、未決事項 |
| AI | STT/LLM構成、カード生成制約、JSON検証、ログ/保存制約、評価指標 |

参照元は主に `Project.md`, `ProjectGoal.md`, `AI_BOOTSTRAP_CONTEXT.md`, `cloud-stt-ai-system-flows.md`, `realtime-question-coach-mock.html` である。`realtime-question-coach-system-flows.md` に含まれる DB、Redis、Postgres、監査ログ、CRM/Notion連携等の案は、現行MVP方針とは異なるため、MVP要件ではなく将来拡張候補として扱う。

## 1. 文書の目的

本書の目的は、Realtime Question Coach の業務目的、対象業務、MVP範囲、機能要件、非機能要件、データ取扱い、AI要件、受入基準を明確にし、以降の設計・実装・評価作業の判断基準にすることである。

本書では「用件」ではなく、業務上満たすべき条件としての「要件」を扱う。

## 2. プロダクト概要

Realtime Question Coach は、会議・商談・面談中にリアルタイム文字起こしを行い、会話の流れに応じて「今聞いておいた方がよい質問」「確認漏れになりそうな論点」「あとで回収すべき事項」を短いカードとして表示するWebアプリケーションである。

主目的は、会議後の要約ではない。会話中に重要論点へ気づける状態を作り、聞き漏れを減らすことが目的である。

基本UIは次の2ペイン構成とする。

| 領域 | 役割 |
| --- | --- |
| 左ペイン | リアルタイム文字起こしを表示する |
| 右ペイン | AIによる質問候補、確認事項、あとで回収すべきカードを表示する |

AIは音声で会話に割り込まない。利用者は、右ペインに表示されるカードを参考情報として確認し、実際に質問するかどうかを会話文脈に基づいて判断する。

## 3. 業務背景と課題

商談、採用面接、要件定義、ユーザーインタビューでは、会話中に重要事項を聞き逃すと、後から回収しにくい。特に次の論点は、会話中に確認できるかどうかが業務品質に直結する。

- 商談: 課題、影響範囲、予算、決裁者、導入時期、成功条件
- 採用面接: 実績、本人の役割、転職理由、チーム経験、期待条件
- 要件定義: 目的、対象ユーザー、必須要件、例外ケース、権限、運用制約
- ユーザーインタビュー: 行動背景、困りごと、代替手段、頻度、判断理由

一方で、AIカードが多すぎると会話の集中を妨げる。したがって本プロダクトでは、AIが常時提案するのではなく、重要語、曖昧表現、未確認項目、話題転換などを契機に必要時だけカードを出す。

## 4. 業務目的と成功状態

### 4.1 業務目的

- 会議・商談・面談中の聞き漏れを減らす。
- 利用者が会話中に「今確認すべき論点」へ気づけるようにする。
- 会話後に「聞いておけばよかった」と気づく項目を減らす。
- カテゴリ別プレイブックにより、会話タイプに応じた質問品質を安定させる。
- 会話データをサーバーに残さない軽量なMVPとして検証できるようにする。

### 4.2 成功状態

MVPの成功状態は次の通りである。

- 録音前に会話カテゴリ、業界、役職、目的、確認論点を設定できる。
- 左ペインに文字起こしが表示される。
- 右ペインに、会話文脈とプレイブックに基づいた質問カードが表示される。
- カードの表示件数には固定上限を設けず、右ペイン内スクロールで全件を確認できる。
- 利用者が `聞いた` / `あとで` / `不要` / `固定` / `再判定` を操作できる。
- 会議後に、聞けたこと、聞けなかったこと、次回確認事項を確認できる。
- 音声ファイルを自社クラウドに保存しない。
- 会話データ用のサーバーDBなしでセッションを完結できる。

## 7. MVP前提とスコープ境界

### 7.1 MVP前提

- Webアプリとして実装する。
- PC / iPad ブラウザで利用できる。
- Next.js / React on Vercel を想定する。
- STTはクラウドSTTを利用する。
- LLMはクラウドLLMを利用する。
- 会話データ保存用のDBは持たない。
- ただし、ログイン、認証、権限管理のための最小限のDB/Auth基盤は利用してよい。候補は Supabase Auth / Supabase Postgres 等とする。
- 音声ファイルは自社クラウドに保存しない。
- 文字起こし、カード、会議後レポートは原則ブラウザ内メモリに保持する。
- ユーザーが明示した場合のみ、ローカル保存またはMarkdown/JSON等でエクスポートする。

### 7.2 MVP全体の対象

- Session Setup
- `sessionProfile` 生成
- カテゴリ別・業界別プレイブック
- ダミー文字起こしからのカード生成
- 2ペインUI
- カード操作
- ログイン / 認証 / 最小限の権限管理
- クラウドSTT接続
- クラウドLLM接続
- AIカードJSON schema
- 会議後レポート
- ローカル保存 / エクスポートの最低限導線

### 7.3 最初の実装単位

MVP全体にはクラウドSTT接続を含める。ただし、最初の実装単位では STT から始めず、次の順に成立させる。

```text
Session Setup
  -> sessionProfile
  -> playbook selection
  -> dummy transcript
  -> AI card generation
```

理由は、カード品質、プレイブック、プロンプト、UI体験を先に検証するためである。STT接続は、カード生成体験が成立した後に統合する。

### 7.4 初期MVPの非対象

- 社内資料検索 / RAG
- Google Drive / Notion / Slack 連携
- CRM連携
- 複数端末同期
- 高度なチーム管理
- 管理者監査
- 課金
- 管理画面
- 音声ファイルのクラウド保存
- デスクトップアプリ
- スマホ専用UI
- ローカルSTT
- ローカルLLM
- AIによる音声発話
- Redis / Postgres / Transcript DB を前提にした会話データの永続保存

## 8. To-Be業務フロー

### 8.1 録音前

1. 利用者は、会話の目的と録音・文字起こし・AI利用のルールを確認する。
2. 必要に応じて、会話相手または社内ルールに基づく同意を取得する。
3. 利用者は Session Setup を開く。
4. 会話カテゴリ、業界、相手役職、フェーズ、目的、商材、必ず確認したい論点、避けたい出力を入力する。
5. アプリは入力内容を `sessionProfile` として構造化する。
6. アプリは `sessionProfile` に基づいてプレイブックを選択する。

### 8.2 会議中

1. 利用者は録音を開始する。
2. ブラウザはマイク権限を取得する。
3. クラウドSTT接続後は、音声をクラウドSTTへ直接ストリーミングする。
4. 左ペインには `partial transcript` と `final transcript` を区別して表示する。
5. AIカード生成には原則 `final transcript` のみを使う。
6. ブラウザは直近1-3分の会話、聞けた項目、未確認項目、カード状態を保持する。
7. local rule gate が重要語、曖昧表現、未確認項目、話題転換などを判定する。
8. 必要時のみ LLM API を呼び、JSON形式のカード候補を取得する。
9. JSON検証と重複除去を経て、右ペインに全active / pinnedカードをスクロール表示する。

### 8.3 カード操作

利用者はカードに対して次の操作を行える。

| 操作 | 意味 |
| --- | --- |
| `聞いた` | 会話中に確認済みとして扱う |
| `あとで` | 後で回収すべき論点として残す |
| `不要` | 文脈に合わない、または不要なカードとして閉じる |
| `固定` | 重要なカードとして見失わないように保持する |
| `再判定` | 現在の文脈でカード生成を再実行する |

これらの操作状態は、会話中のUI制御、会議後レポート、カード品質評価の材料にする。

### 8.4 会議終了

1. 利用者が終了操作を行う。
2. 音声ストリームを停止する。
3. final transcript を確定する。
4. 必要最小限のテキストを使い、会議後レポートを生成する。
5. 利用者は、聞けたこと、聞けなかったこと、次回確認事項を確認する。
6. 利用者は、破棄、ローカル保存、Markdown/JSONエクスポートのいずれかを選択する。
7. 保存しない場合、ブラウザメモリ上のセッションデータを破棄する。

### 8.5 改善ループ

1. 会話サンプルを追加する。
2. `sessionProfile` を設定する。
3. 対応するプレイブックを選択する。
4. AIカードを生成する。
5. 人間がカードを評価する。
6. bad case を分類する。
7. プレイブック、プロンプト、local rule を修正する。
8. 再実行して改善効果を確認する。

## 10. 機能要件

### 10.1 ログイン / 権限管理

| ID | 要件 |
| --- | --- |
| AUTH-001 | 利用者はログインしてアプリを利用できる。 |
| AUTH-002 | 認証・権限管理のために限り、Supabase Auth / Supabase Postgres 等のDB利用を許容する。 |
| AUTH-003 | DBに保存する情報は、ユーザーID、メール、認証プロバイダ、権限ロール、作成/更新日時などの認証・権限メタデータに限定する。 |

| --- | --- |

## 11. AI / STT / LLM要件

### 11.1 アーキテクチャ要件

| ID | 要件 |
| --- | --- |
| AI-001 | 音声はブラウザからクラウドSTTへ直接ストリーミングする。 |
| AI-002 | Vercel / Next API は長時間音声ストリームを中継しない。 |

### 11.2 カード生成制約

| ID | 要件 |
| --- | --- |
| AI-006 | 専門知識はLLMの一般知識だけに任せず、プレイブックで補う。 |
| AI-007 | プレイブックは `mustCheck`, `signals`, `goodQuestions`, `avoid`, `completionCriteria` を持つ。 |
| AI-008 | 通常のLLM文脈レビューは40秒に1回以下を目標にする。 |
| AI-009 | 高重要度でも16秒のクールダウンを設ける。 |
| AI-010 | 手動再判定は即時実行できるが、濫用対策としてレート制限を検討する。 |
| AI-011 | 1回のLLM応答候補は最大3件とし、表示中カードには固定件数上限を設けない。 |
| AI-012 | カードJSONは形式、件数、長さを検証する。 |
| AI-013 | 根拠なく断定するカードを抑制する。 |
| AI-014 | カード候補には `urgency`, `impact`, `confidence`, `topicFreshness`, `mustCheckGap`, `dedupeKey` を持たせ、表示優先度を計算できるようにする。 |
| AI-015 | 表示対象は `active` / `pinned` とし、固定スロット上限を設けない。`queued`, `later`, `dismissed`, `done` の状態も管理する。 |
| AI-016 | 新規カードが既存カードと同じ `dedupeKey` を持つ場合は、新規表示ではなく既存カードの内容・優先度更新として扱う。 |
| AI-017 | 重複していない候補はactiveとして追加し、スコアを優先度表示に利用する。 |
| AI-018 | 表示件数を理由に既存カードを自動降格・入れ替えしない。 |
| AI-019 | `later`, `done`, `dismissed` への移動はユーザー操作または論点状態に基づいて行う。 |
| AI-020 | `pinned` カードは自動降格しない。ただし、重大な未確認事項が発生した場合は、UI上で新規高優先カードがあることを明示する。 |
| AI-021 | `done` カードはactiveから外し、同一論点の再表示を抑制する。 |
| AI-022 | `dismissed` カードは一定時間または同一トピック内では再表示を抑制する。ただし新情報により重要度が上がった場合は再候補化できる。 |
| AI-023 | `later` カードはactive枠から外し、会議後レポートまたはあとで回収リストに残す。 |

### 11.3 カード表示スコアリング方針

カード表示スコアは、少なくとも次の要素で決める。

| 要素 | 例 | 重みの考え方 |
| --- | --- | --- |
| 緊急度 | 今聞かないと会話が次に進む | 高 |
| 業務影響 | 予算、決裁者、期限、対象範囲、責任者 | 高 |
| 未確認度 | `mustCheck` に残っている | 高 |
| 新規性 | 既存カードと重複していない | 中 |
| 文脈適合度 | 会話タイプ、業界、目的に合う | 中 |
| 信頼度 | STTと文脈から十分に根拠がある | 中 |
| ユーザー操作 | `不要` 済み、`聞いた` 済み、`固定` 済み | 抑制または保護 |

表示制御の基本ルールは次の通りとする。

1. active / pinnedカードには固定件数上限を設けない。
2. 新規候補はスコアリングと重複判定を通す。
3. 重複していない新規候補はactiveへ追加する。
4. 表示件数を理由に既存カードを自動降格・入れ替えしない。
5. `pinned` は固定表示を維持する。
6. `done` / `dismissed` は同一論点の再表示を抑制する。
7. 手動 `再判定` では active / queued / later を再評価する。
8. 右ペイン内のスクロールで全active / pinnedカードへ到達できるようにする。

### 11.4 評価と改善

bad case は少なくとも次の分類で評価する。

| 分類 | 意味 |
| --- | --- |
| `too_generic` | 質問が一般的すぎる |
| `too_late` | カードが出るタイミングが遅い |
| `too_many` | カードが多すぎる |
| `missed_important` | 重要論点を拾えていない |
| `wrong_context` | 業界や会話目的に合っていない |
| `unsafe_claim` | 根拠なく断定している |

## 12. データ要件

| データ | 主な項目 | 保存方針 |
| --- | --- | --- |
| auth user | userId, email, provider, role, createdAt, updatedAt | 認証・権限管理DB。会話本文は保存しない |
| `sessionProfile` | meetingType, industry, counterpartRole, phase, goal, productCategory, mustCheck, avoid | ブラウザ内状態。必要時のみローカル保存 |
| `playbook` | mustCheck, signals, goodQuestions, avoid, completionCriteria | アプリ内管理。MVPではローカル/静的管理を想定 |
| transcript | partial, final, speaker, timestamp | 原則ブラウザメモリ。サーバーDB保存なし |
| conversation buffer | 直近1-3分のfinal transcript、聞けた項目、未確認項目 | ブラウザメモリ |
| coach card | shouldShow, priority, title, question, reason | ブラウザメモリ |
| card action state | done, later, dismissed, pinned | ブラウザメモリ |
| session report | heard, missed, nextActions | ブラウザメモリ。ユーザー明示時のみローカル保存/エクスポート |

### 12.1 保存と送信の整理

本プロダクトでは「保存しない」と「送信しない」を区別する。

| 対象 | 方針 |
| --- | --- |
| 音声 | クラウドSTTへ送信するが、自社クラウドには音声ファイルとして保存しない |
| 文字起こし | ブラウザ内メモリに保持する。サーバーDBには保存しない |
| LLM入力 | 必要最小限のテキストだけ送信する |
| LLM応答 | JSON検証後にブラウザへ返す。サーバーDBには保存しない |
| 認証・権限情報 | Supabase Auth / Supabase Postgres 等に保存してよい。ただし会話本文、音声、AIカード、会議後レポートは含めない |
| ローカル保存 | ユーザーの明示操作時のみ行う |
| エクスポート | ユーザーの明示操作時のみMarkdown/JSON等で出力する |

### 12.2 通信時の暗号化

ブラウザメモリを基本とする場合でも、STT、LLM、認証基盤、Vercel APIへ送信するデータは通信経路上で第三者に傍受されるリスクがある。そのため、サーバーまたは外部プロバイダへ送信する通信は、暗号化された通信路のみを許可する。

| 経路 | 要件 |
| --- | --- |
| Browser -> Vercel / Next API | HTTPSのみ。平文HTTPは禁止 |
| Browser -> Cloud STT | HTTPS / WSS 等の暗号化ストリーミングのみ |
| Vercel / Next API -> Cloud LLM | HTTPSのみ |
| Browser / API -> Auth基盤 | HTTPSのみ |
| ローカル保存 | ユーザー端末管理。必要に応じてブラウザ/OSの保護機能に依存 |

暗号化は通信経路上の傍受対策である。STT/LLMプロバイダ側で処理されるデータの保持・学習利用・ログ保存については、別途 no-training / retention / logging の設定確認を必須とする。

## 14. 成功指標

| 指標 | 初期目標 | 意味 |
| --- | --- | --- |
| 有用カード率 | 60%以上 | 表示されたカードのうち、実際に聞く価値があった割合 |
| 邪魔カード率 | 25%以下 | 表示されない方がよかったカードの割合 |
| 聞き漏れ削減率 | 初期評価で計測 | 会議後に「聞けばよかった」と感じた項目がどれだけ減ったか |
| 初回カード表示速度 | 10秒以内 | 重要論点が出てからカードが出るまでの時間 |
| LLM呼び出し頻度 | 通常の文脈レビューは40秒に1回以下、高重要度時は16秒クールダウン | リアルタイム中のAPI呼び出し制御 |
| 表示中カード数 | 固定上限なし、LLM応答1回は最大3候補 | スクロールで全件へ到達しつつ1回の追加量を抑える |
| カード採用率 | 初期評価で計測 | `聞いた` / `固定` / `あとで` にされたカードの割合 |
| 重複カード率 | 継続改善 | 同じ論点のカードが繰り返し出る割合 |
| unsafe_claim率 | 継続改善 | 根拠なく断定するカードの割合 |

## 15. 受入基準

### 15.1 最初の実装単位の受入基準

- Session Setupでカテゴリ、業界、役職、目的、確認論点を入力できる。
- 入力内容から `sessionProfile` が生成される。
- 会話カテゴリに応じてプレイブックが選択される。
- ダミー文字起こしから質問カードが生成される。
- 2ペインUIで左に文字起こし、右にAIカードが表示される。
- 7件以上のカードも保持され、内部スクロールで全active / pinnedカードを確認でき、表示件数を理由に既存カードが降格しない。
- カードにタイトル、質問、根拠、優先度が表示される。
- `聞いた` / `あとで` / `不要` / `固定` / `再判定` が操作できる。
- 会話カテゴリを切り替えると、カード内容または判定モードが変わる。

### 15.2 MVP全体の受入基準

- ログインできる。
- 最小限の権限ロールを扱える。
- ブラウザで録音を開始できる。
- マイク権限を取得できる。
- ブラウザ/OSが許可する場合、Webタブ音声またはシステム音声を入力ソースにできる。
- STT短命トークンを発行できる。
- ブラウザからクラウドSTTへ直接ストリーミングできる。
- `partial transcript` と `final transcript` を区別して表示できる。
- `final transcript` を会話バッファへ追加できる。
- local rule gate により、不要なLLM呼び出しを抑制できる。
- LLM応答をJSON schemaで検証できる。
- 会議終了後に、聞けたこと、聞けなかったこと、次回確認事項を確認できる。
- 会話データ用のサーバーDBなしでセッションを完結できる。
- 音声ファイルを自社クラウドに保存しない設計が維持される。
- Vercelログに本文、音声、LLM入力、LLM応答が出ない。
- ブラウザ、Vercel/Next API、Cloud STT、Cloud LLM、Auth基盤間の通信がHTTPS/WSS/TLS等で暗号化されている。
- 認証・権限DBに、会話本文、音声、AIカード、会議後レポートが保存されていない。

## 16. リスクと対応方針

| リスク | 影響 | 対応方針 |
| --- | --- | --- |
| STT精度が低い | カード精度が落ちる | ダミー文字起こしで先にカード品質を検証し、STT評価を別途行う |
| カードが多すぎる | 会話を邪魔する | local rule gate、40秒レビュー、16秒クールダウン、重複除去、1応答最大3候補、右ペイン内スクロールを設ける |
| カードが一般的すぎる | 利用価値が下がる | プレイブックをカテゴリ別・業界別に整備する |
| 重要論点を拾えない | 聞き漏れ削減に失敗する | bad case分類と人間評価で改善する |
| AIが根拠なく断定する | 誤誘導につながる | `reason` 表示、avoidルール、unsafe_claim評価を行う |
| 外部送信の説明不足 | 利用停止や信頼低下につながる | 同意文言とUI文言で明示する |
| Vercelログに本文が残る | プライバシーリスク | ログ設計とレビュー観点を明文化する |
| iPad Safari制約 | 利用体験が崩れる | 早期に実機検証する |
| 会話データDBなし制約 | B2B管理機能が不足する | MVPでは価値検証優先。チーム管理・監査は将来拡張に分離する |
